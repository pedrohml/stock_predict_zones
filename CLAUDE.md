# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A three-step pipeline that turns price candles into support/resistance zones with probabilities and plots them. Each step exchanges plain JSON:

```
build_prompt.py  ──input.json──►  reversal-zones-projection skill (Claude)  ──projection.json──►  plot_projection.py
```

`README.md` is the full user-facing reference (CLI options, both JSON formats, glossary, known limits, roadmap). Keep it in sync when changing a CLI flag or a JSON field.

## Commands

```bash
uv sync                                                                      # Python 3.12+ (.python-version); also installs the `zones` command
uv run zones PETR4.SA --horizon 1-3m                                         # all steps: Yahoo, headless `claude -p`, rz.py check, chart, trade setups (--no-entries to skip), into runs/TICKER/TIME_HORIZON/
uv run python run_pipeline.py PETR4.SA --horizon 1-3m                        # the same thing; `zones` is run_pipeline.main
uv run zones list [TICKER]                                                   # saved projections (rz.py list); `zones runs [TICKER]`: the folders under ./runs
uv run zones score [TICKER | FOLDER] [--json]                                # score_projections.py, hits Yahoo Finance
uv run zones backtest TICKER... [backtest.py options]                       # backtest.py, hits Yahoo Finance
uv run zones plot WHAT [-o FILE] [plot options]                              # plot_projection.py for a run; WHAT: a folder with the pair, or a ticker (latest run, else latest saved)
uv run zones show WHAT                                                       # show_run.py; `zones entries WHAT`: trade_entries.py build, then check
uv tool install --editable .                                                 # optional: `zones` in any directory, still running this checkout
uv run zones --show-config                                                   # config files found, every setting and where its value comes from (--init-config writes a template, --no-config ignores the files)
uv run python build_prompt.py PETR4.SA --horizon 1-3m -o petr4_input.json    # step 1, hits Yahoo Finance
uv run python plot_projection.py petr4_input.json petr4_projection.json -o petr4.png   # step 3
uv run python show_run.py FOLDER | INPUT.json PROJECTION.json [ENTRIES.json]   # one run as a text summary (what `zones` prints before the file paths)
uv run python score_projections.py [FOLDER] [--ticker T] [--json]            # saved projections vs later prices, hits Yahoo Finance
uv run python backtest.py PETR4.SA NVDA --horizon 1-3m [--json] [--csv F]     # baseline probabilities on past dates, hits Yahoo, no Claude (also `zones backtest`)
uv run python value_test.py T... --out DIR [--max-cost USD] [--jobs N]          # PAID: Claude's adjustment vs the baseline on dates after the model's training cutoff; resumes in DIR
uv run zones batch watchlist.txt --jobs 2 --max-cost 5 [pipeline options]    # one pipeline run per ticker, summary.csv in runs/batch/TIME/
uv run pytest                                                                # all tests, offline, a few seconds
uv run pytest tests/test_rz.py::test_sim_output_structure                    # a single test
```

The tests in `tests/` never touch the network: they cover the pure functions of `build_prompt.py`, `rz.py`, a plot smoke test, `run_pipeline.py` with Yahoo and Claude stubbed (its config files in `tests/test_config.py`), `score_projections.py` and `backtest.py` with Yahoo stubbed, `value_test.py` with Yahoo and its `launch()` stubbed, `batch_runs.py` (fake child runs, plus the real pipeline in the child with Yahoo and `claude` stubbed), the live output of `build_prompt.py` byte for byte with a fake Yahoo and a frozen clock (`tests/test_build_prompt_live.py`, expected files in `tests/fixtures/build_prompt_live/`; regenerate them only for a deliberate output change), and the cross-file contracts below (`tests/test_contracts.py`). `tests/fixtures/input.json` is synthetic; regenerate it with `uv run python tests/fixtures/make_input.py`. There is no linter or CI, and nothing tests the Yahoo download itself, so still run the scripts end to end after changing them.

No test may read the developer's own config file: the autouse `no_real_config` fixture in `tests/conftest.py` points `ZONES_CONFIG` at a file that does not exist, turns the `./zones.toml` lookup off (`run_pipeline.PROJECT_CONFIG = None`) and puts `RZ_PROJECTIONS_DIR` back after each test. A test about config files sets `ZONES_CONFIG` to its own temp file (and `PROJECT_CONFIG` back to `"zones.toml"` after a `chdir` to a temp folder). When checking by hand, set `ZONES_CONFIG` (or `HOME`/`XDG_CONFIG_HOME`) to a temp path; never write to the real `~/.config`.

Step 2 is the `reversal-zones-projection` project skill: given an input JSON, Claude follows `.claude/skills/reversal-zones-projection/SKILL.md`. Its helper can also be run directly:

```bash
RZ=.claude/skills/reversal-zones-projection/scripts/rz.py
uv run python $RZ levels input.json              # facts for choosing zones
uv run python $RZ sim    input.json zones.json   # baseline probabilities
uv run python $RZ check  output.json             # validate a projection; prints OK or the violations
uv run python $RZ save   input.json output.json  # keep the pair under projections/TICKER/TIME_HORIZON/
uv run python $RZ list                           # saved projections, oldest first, open or ended
uv run python $RZ score  input.json output.json candles.json   # outcome of one projection from a candles file, offline
```

Use `rz.py check` on any projection JSON you write or edit by hand.

The skill saves every projection by default (`rz.py save`, its last workflow step) so past projections can be scored later. `projections/` is gitignored, relative to the working directory (override with `RZ_PROJECTIONS_DIR` or a trailing folder argument), and append-only: `save` never overwrites and nothing should edit or delete an earlier entry.

`examples/` holds a ready-made input/projection pair (`petr4_input.json`, `petr4_projection.json`) for trying `plot_projection.py` and `rz.py check` without Yahoo or step 2.

## Architecture

- **`build_prompt.py`** (step 1): `PRESETS` maps each horizon to a main series, an optional coarser context series, the `close_basis` and the probability meaning. The context series is filtered to candles that start *before* the main series, so the two never overlap. `render()` uses placeholder substitution to keep each candle row and event on one line inside otherwise indented JSON. Only `build()`, `history()` and `upcoming_events()` touch Yahoo; `make_series()`, `make_all_series(args, candles_of, ...)` (the series of a horizon, from a function that returns the candles of one preset entry) and `assemble()` (the JSON from its parts) are offline, so `backtest.py` builds past inputs with the same code. `build()` stamps `schema_version` (`SCHEMA_VERSION`) and a `provenance` block (`provenance()`: source, library version, UTC download time, `auto_adjust: false`, per series rows/first/last/what was requested, and `data_sha256` = `data_hash(data)`, the sha256 of `data` in canonical JSON). `provenance()` reads everything from the finished prompt, so another way of building an input (e.g. from stored candles) can call it with its own `source`.
- **`.claude/skills/reversal-zones-projection/`** (step 2): `SKILL.md` is the prompt that defines the workflow, the zone-selection rules, the limits on adjusting simulated probabilities and the exact output schema. `scripts/rz.py` is its helper (Monte Carlo with a fixed seed, so the same input and zones give the same baseline).
- **`score_projections.py`** (after the fact): reads each saved folder's optional `provenance.json` (`made_by()`) to name the model and rules per projection, and `by_model()` adds a Brier score per model to the calibration (no file: `unrecorded`). It walks the saved history with `rz.saved()`, downloads daily candles once per ticker (`download()`, the only function that touches Yahoo; tests stub it), builds weekly/monthly candles from them (`aggregate()`), and calls `rz.outcome()` per projection. `calibration()` buckets the forecasts of ended projections and computes Brier scores. It loads `rz.py` by path, like the plot.
- **`backtest.py`** (baseline on past dates): `download()` is the only function that touches Yahoo (tests stub it): daily candles once per ticker. `input_as_of()` slices them at the as-of day *before* anything else and builds the input with `build_prompt.make_all_series()`/`assemble()`, weekly/monthly candles from `score_projections.aggregate()`. `choose_zones()` is the one place the mechanical zone rule lives (`RULE` describes it; README repeats it), reading `rz.facts()`. Then `rz.baseline()` and `rz.outcome()`, and the summary reuses `score_projections.calibration()`, `brier()` and `buckets()`. `DEFAULT_PATHS` is read from `rz.baseline`'s signature. `tests/test_backtest.py` pins no look-ahead (the input from all candles equals the input from candles cut at the as-of day).
- **Outcome definitions live in `rz.py`**, not in the scorer: `reached()` and `middles()` are the single implementation of "reached", "broken" and the scenario lines, used by `sim()` on 200,000 simulated paths and by `outcome()` on the one realised path. `realised()` picks the horizon's candles and mirrors `schedule()`. `tests/test_rz_outcome.py` feeds `walk()`'s simulated paths to `outcome()` as candles and requires the frequencies to reproduce `sim()`; change one side only with that test green. `walk()` must keep drawing the same random numbers in the same order (baselines are reproducible). `levels`/`sim` print what `facts()`/`baseline()` return; `unpack()` is `load()` for a dict already read. Code that needs the numbers calls those, not the printing commands.
- **`plot_projection.py`** (step 3): one `build()` function that draws five matplotlib axes (candles + zones, probability bars sharing the price axis, scenario bar, notes, side panel). `THEMES` and `TEXT` hold all colours and translated strings, including each language's number separators and intraday tick format. Labels are placed by measuring text with the figure's renderer (`extent()`, `spread()`, `share_lines()`), not by fixed offsets; `tests/test_plot_layout.py` pins that with text boxes, never pixels.
- **`trade_entries.py`** (trade setups): `setups()` and `pick()` are the template's rules in code; prices (stop, risk, reward, units) are rounded to `places(source)`, the precision of the input's candle rows (at least 2), and `problems()` compares prices to that precision (`price_tolerance()`), the rest to 0.011; a setup whose risk rounds to zero is discarded, and an error reply is accepted when the files are unusable or no setup passes; `build()` turns them into the whole reply, writing its sentences from `TEXT` (one entry per language, like the chart's), so the default path needs no Claude; `fill()` builds the prompt from `prompts/trade_entries.md` for `--entries-by-claude`; `problems()` checks a reply, computed or Claude's, against the schema and those rules. See Domain constraint.
- **`run_pipeline.py`** (all steps): a thin orchestrator that shares no code with the others. It runs the two scripts and `rz.py check` as subprocesses and step 2 as `claude -p` (`claude_command()` holds the exact flags and the tool allowlist, `call_claude()` is the only place that starts Claude). Step 2 asks for `--output-format stream-json --verbose` (one JSON event per line): `call_claude()` drains stdout and stderr in two threads and enforces the timeout itself, `Progress` maps tool calls to the skill's stages (`STAGES`, one stderr line each, heartbeat after a silence, nothing with `--quiet`) and skips every event or line it does not know, and `claude_result()` finds the final `result` event, from which `summary()` prints duration, turns and cost (a field Claude Code does not report is left out, never guessed). A new helper subcommand or work-file name in the skill needs a matching entry in `STAGES`/`Progress.stage()` to show up. Options it does not declare go to `build_prompt.py` untouched, so a new step-1 flag needs no change here; plot options are forwarded only when given, so step 3 keeps its own defaults. Output: without `--out-dir`, `run_folder()` makes a new `runs/TICKER/TIME_HORIZON/` under the current directory (named like `rz.py save` names its folders, from the input's `asset.ticker`, `now.time` and `horizon`, with `_2`, `_3` ... when taken) holding `input.json`, `projection.json` and `chart.png`, with files given by `--input`/`--projection` copied in so every folder is complete; plotting again with `--chart` makes no folder. With `--out-dir` the files go exactly there as `STEM_*` (stem from the ticker or `--name`) and given files are not copied. Nothing is created before the input and the given projection have loaded, and `build_prompt.py` writes into a throwaway folder. `runs/` is disposable output; `projections/` stays the append-only record, and the two are never merged. `--open` calls `open_chart()` after a successful run (`start_viewer()` is the only place that starts a viewer; failure is one warning). When the input's `research` is not `none` its prompt (`claude_prompt()`) restates in two lines the skill's research rule (every driver `source` and event size comes from a page opened with WebFetch) and names the tools; the rule itself lives in `SKILL.md`, because drivers written from the search summary alone did not match their sources in real runs. It tells Claude to skip the skill's save step and runs `rz.py save` itself after `check` (not with `--projection` or `--no-save`), so each run is kept exactly once; a failed save only warns. Provenance (section `# ---- provenance` in `run_pipeline.py`): `project()` returns `claude_facts()` of the stream (model and `claude_code_version` from the `system` init event, turns/cost/durations/usage from the `result` event, `modelUsage` keys as `models_used`; absent fields stay absent), and after `check`/`save` `run_provenance()` writes `provenance.json` (`STEM_provenance.json` with `--out-dir`) into the run folder and the saved folder: input/projection sha256, the input's own `provenance`, both `schema_version`s, the Claude facts, and `rules_provenance()` (sha256 of every `RULE_FILES` entry, a 12-hex `version` over them, git commit and dirty flag via `git_state()`). The entries step adds an `entries` block and rewrites both copies in the same run. A run with `--projection` writes none (it copies a sibling provenance into a new run folder, never overwrites one). A new rule file belongs in `RULE_FILES`. The tests stub `run` (for Yahoo) and `call_claude` (or replace the `claude` binary with a script that replays `tests/fixtures/claude_stream.jsonl`, a cut-down recording of one real run), and point `RZ_PROJECTIONS_DIR` at a temp folder so they never write into the repo's `projections/`. Personal defaults: `parse()` ends in `configured()`, which reads the user file (`user_config()`: `$ZONES_CONFIG`, else `$XDG_CONFIG_HOME/zones/config.toml`, else `~/.config/zones/config.toml`) and `./zones.toml`, and `settle()` is the single implementation of the precedence command line > environment variable (`RZ_PROJECTIONS_DIR`, for `history_dir` only) > project file > user file > built-in default (documented once, in README "Your defaults"). `SETTINGS` lists what a file may set; a key is the option's name with underscores. Own options have `None` as their argparse default so that "typed" can be told from "default", and `configured()` fills `args` with the settled values (`args.no_entries`/`args.no_save` are derived from `entries`/`save`, and switches are `BooleanOptionalAction`, so each has a `--no-` form), which is why `pipeline()` needed no change beyond `args.runs_dir`. Step-1 settings are the exception to "a new step-1 flag needs no change here": `SETTINGS` repeats their names, choices and defaults (and the chart's themes and languages) so that a bad config value fails before any download or Claude call; `tests/test_config.py` compares them with `build_prompt.arguments()` and `plot_projection.THEMES`/`TEXT`, and a step-1 flag that is not in `SETTINGS` still passes through from the command line, it just cannot be set in a file. `step1_arguments()` turns file values into `--opt=value` arguments placed *before* the user's own, only for options not typed in this run (`typed()` sees `--opt value`, `--opt=value` and abbreviations) and never with `--input`; `--no-volume` is declared here because `build_prompt.py` has no off form. `history_dir` from a file or `--history-dir` is exported as `RZ_PROJECTIONS_DIR` for the whole process in `configured()`, never over a variable that is already set by the user. Paths in a file are resolved against the file's folder (`config_path()`). Config problems are a `PipelineError` that `parse()` prints as one `Error:` line before exiting 1; `--show-config` and `--init-config` exit from `parse()` too, so `main()` is untouched. A test that runs `main()` without `--out-dir` must first `chdir` to a temp folder (the autouse fixture in `tests/test_run_pipeline_outputs.py`), or it writes `runs/` into the repo, and must stub `start_viewer` before passing `--open`.
- **`value_test.py`** (does the paid step 2 beat the free baseline?): imports `backtest.py` and changes nothing in it. Per (ticker, as-of date) it writes `OUT/cases/TICKER/DATE/input.json` with `backtest.input_as_of()` (research none, no events), runs the real pipeline on it (`pipeline_command()`: `run_pipeline.py --no-config --input ... --no-entries --no-save --model M --out-dir CASE --name case`; `launch()` is the only place that starts it, and `tests/conftest.py`'s `no_real_claude` replaces it with a function that raises), then scores three versions with `rz.outcome()`: Claude's projection, `rz.baseline()` on Claude's own zone edges (`bt.projection()`), and `bt.run_case()` (mechanical zones). Cost comes from `case_provenance.json` (`total_cost_usd`), else the `$` on the pipeline's summary line; a run that never reached Claude (no `[2/` header) costs 0 and writes `not_started.json` instead of `run.json`, so it is retried. `run.json` means paid: a resumed `--out` never launches that case again, failed or not. `Budget` starts a run only while spent + (runs in flight + 1) x reserve <= `--max-cost` (reserve = highest cost seen, `FIRST_RESERVE` before any). Look-ahead: `TRAINING_CUTOFF` (model id -> month, only from Anthropic's models overview, `CUTOFF_SOURCE`) refuses a `--start` on or before the cutoff, and `score_case()` drops a run whose reported model is unknown there or too recent. Candles are cached in `OUT/data/` so a resume scores the same prices. Tests: `tests/test_value_test.py` (stubbed Yahoo and a fake `launch` that writes the files the pipeline would).
- **`run_pipeline.py`, the commands after a run**: `main()` starts with `dispatch()`, which runs `zones list|runs|score|plot|show|entries|backtest|batch` (`COMMANDS`, one function each) and otherwise hands the arguments to `parse()` unchanged. A first argument is a command only when it is exactly one of those lowercase words, so `zones nvda`, `zones LIST`, `--input` and `--help` stay the pipeline's; `run` and `--` are stripped and force the pipeline (`zones run list`). The commands are as thin as the pipeline: `relay()` runs a script on the user's terminal and returns its exit code (`score_projections.py`, `plot_projection.py`, `show_run.py`, `backtest.py` with every argument passed on), `run()` captures where the output is filtered or checked (`rz.py list`, which has no ticker filter, and `trade_entries.py build` then `check` into a temp file). Options a command does not declare are passed on, which is why WHAT must come first (`what_first()`): a later word may be an option's value. `resolve()` turns WHAT into one run: a folder holding the pair (`pair()`: plain names, or one `STEM_` pair, `--name` to pick), a folder with such folders below it, or a ticker, looked up case-insensitively in `./runs` first and then in the history (`history()`: `$RZ_PROJECTIONS_DIR`, else `./projections`), latest by folder name (`folder_key()`: time, then `_N`; `FOLDER_NAME` must keep matching what `run_folder()` and `rz.py save` produce), narrowed by `--horizon`. `target()` decides where `plot` and `entries` write: beside the pair for a run (replacing `chart.png`/`entries.json`), the current directory for a saved projection, and never inside the history (`kept()`), `-o` included. `runs` reads folder names only. Before a command runs, `command_config()` reads the same config files as `configured()` and applies `runs_dir` (as `runs_home`), `history_dir` (exported, never over a set `RZ_PROJECTIONS_DIR`) and the chart settings (`chart_config`: `plot` gets theme/lang/candles/dpi/open, `show` gets lang, each only when not typed, via `configured_options()`); a bad file is the same one-line error. Tests: `tests/test_zones_commands.py` (stub `relay` for `score`; copy its autouse `cwd` and `store` fixtures).
- **`show_run.py`** (the summary `zones` ends with): `summary()` turns an input, a projection and optionally an entries file into lines of `(text, style)` segments, top to bottom like the chart; `table()` folds columns that do not fit into a second block instead of cutting them, and `render()` clips every line to the width and adds ANSI codes only when asked. It adds no words of its own beyond the labels in its `TEXT` (one entry per language; the keys it shares with the chart, the number separators and `price_digits()` are copies of `plot_projection.py`'s, which it must not import because of matplotlib, and `tests/test_show_run.py` pins them equal). Only what the plot's validation requires is required (`required()`); a malformed optional section is skipped. `run_pipeline.py` runs it as a subprocess after a successful run (`show_summary()`, off with `--no-summary`, any failure is one warning) and relays the output before the file paths; because the script then writes into a pipe, the pipeline passes `--color --width N` when its own stdout is a terminal and `--no-color` otherwise, and `NO_COLOR` always wins. See Domain constraint: no label may read as advice, and the setups keep the note of their own file.

- **`batch_runs.py`** (`zones batch`): the pipeline over a watchlist. `run_pipeline.batch()` imports it and calls `main()` in-process (not relayed, so Ctrl-C reaches its loop and the summary is still written); it imports `run_pipeline` for small helpers and `command_config()` (to find `runs_dir`). Each ticker is a child process `run_pipeline.py run TICKER [options]` (`child_command()`, `PIPELINE`), with stdout and stderr into `RUNS_DIR/batch/TIME/logs/TICKER.log`; `Batch.run()` is a polling loop (no threads) that starts up to `--jobs` children, stops starting new ones once the reported costs reach `--max-cost`, and rewrites `summary.csv` after every run. It duplicates no pipeline logic: it reads what the run printed (see the contract below) and the run folder's `projection.json`. The batch folder name has no `_HORIZON`, so `FOLDER_NAME` and `zones runs` do not take it for a run.

### Contracts that span files

The three pieces share no code, only JSON conventions. Changing one side silently breaks another:

- **Backtest and step 1 share the input builder.** A change to `PRESETS`, `make_all_series()` or `assemble()` changes past inputs in `backtest.py` too; a change to `rz.levels` output keys (`typical_zone_width`, `pivot_*`, `recent_*`, `retracements`, `swing`) needs `choose_zones()` to follow. `backtest.py` supports the daily-or-coarser horizons only (`HORIZONS`); a new one needs an entry in `DEFAULT_STEP`.
- **Main series selection** is implemented twice, identically: the series whose `candles` equals `close_basis`, falling back to the last series (`load()` in `rz.py`, `build()` in `plot_projection.py`). `build_prompt.py` guarantees this by inserting the context series *first*.
- **Horizon and candle labels**: adding a horizon or interval means touching `PRESETS`/`LABEL` in `build_prompt.py`, `HORIZON_DAYS`/`CANDLE_DAYS`/`schedule()` in `rz.py`, the horizon tables in `SKILL.md`, and `TEXT[*]["labels"]` in `plot_projection.py`.
- **`last_row: "forming"`** shortens the first simulation step in `rz.py` and removes one future slot in the plot.
- **Validation**: `plot_projection.py` `preflight()` runs before `build()` and reports every problem at once (exit 1, no traceback). `validate()` covers what `build()` reads, so a new `[...]` access in `build()` needs a matching check there. The projection's rules are not duplicated: the plot loads `rz.py` by path (`RZ_PATH`) and calls `problems(proj, complete=False)`; `rz.py check`/`save` call the same function with `complete=True`. Rule violations block the plot unless `--no-check`; without `rz.py` the plot checks structure only and says so.
- **Tails** are zone entries with a `null` edge and ids `below`/`above`; the plot separates them from real zones by testing for `None`.
- **Scenario thresholds**: the plot recovers the middle-zone prices by regex from the scenario `low`/`high` strings (`"below 40.6"`), whose format comes from `rz.py sim`. Keep a number in those strings.
- **Swing markers** are drawn only if `structure.swing.*[1]` exactly equals a row's `start` string.
- **What a run prints** is read by `batch_runs.py`: the step headers that start Claude Code (`[2/N] Projection: Claude Code runs`, `[5/5] Trade setups: Claude Code writes`), the line `summary()` prints when a call ends (`done in`/`stopped after` ... `$X.XX`), the `Error: ` line, and the `input:` path on stdout. A call that started without its `summary()` line counts as an unknown cost, never zero. `tests/test_batch_runs.py::test_real_pipeline_runs_cost_folders_and_failures` runs the real pipeline in the child to pin these; change those strings only with it green.
- **Schema keys, ids and scenario names stay English** regardless of language; only free-text values are translated.
- **Schema versions and provenance.** The input carries `schema_version` (`build_prompt.SCHEMA_VERSION`) and `provenance`; the projection carries `schema_version` (SKILL.md's example; `rz.SCHEMA_VERSIONS` lists what `check` accepts); `provenance.json` has its own (`run_pipeline.PROVENANCE_VERSION`). All three are optional for readers: inputs and projections without them (every one made before, and `examples/` and `tests/fixtures/` on purpose) must still check, plot, score and show. Raise a version when a field changes meaning or goes away, and add the new value to `rz.SCHEMA_VERSIONS`. The model and cost never go into the projection: Claude cannot report them reliably, so `run_pipeline.py` reads them from the stream. `rz.saved()`, `list`, `score` and `show_run.py` must keep ignoring extra files in a saved folder (`entries.json`, `provenance.json`); `show_run.provenance_file()` and `run_pipeline.provenance_beside()` find the file next to a projection the same way. `tests/test_provenance.py` pins these.

### Things that are easy to get wrong

- One language setting: `build_prompt.py --language` (default `en`, free text) is stored as `reply.language`, sets the language of the projection's free text, and `plot_projection.py` follows it for the chart's own labels (`chart_language()`: primary subtag, so `pt-BR` -> `pt`; no `TEXT` entry or no `reply` -> `FALLBACK_LANG`). `--lang` has no default of its own: it is only an override, and it translates the labels, not the projection's text. A new chart language is one new `TEXT` entry, nothing else.
- Prices are split-adjusted but deliberately **not** dividend-adjusted (`auto_adjust=False`); the `drop` shock in `rz.py` and the chart footer depend on that.
- The project is installable only as an editable install, and is still not a package directory: the code is the root scripts. `pyproject.toml` has a `hatchling` build system and one entry point, `zones = "run_pipeline:main"`, whose wheel holds `run_pipeline.py` alone (`uv_build` cannot build a flat module). `run_pipeline.py` finds the other scripts and the skill next to its own file (`ROOT`) and runs Claude Code there, so `uv sync` and `uv tool install --editable .` work, and a non-editable install stops with a message saying so. Do not move the scripts without changing `ROOT`.
- The skill is a project skill, so Claude Code in this repo always uses the current files. A copy installed elsewhere (claude.ai, `~/.claude/skills/`) does not follow edits made here.
- `rz.py` must not be rewritten per run or have its seed changed: reproducible baselines are a design requirement.
- Session and week-end logic assumes a Monday-to-Friday exchange, so crypto tickers get wrong `forming` labels (listed under Known limits in the README).

## Domain constraint

One deliberate exception: ranked trade setups. `run_pipeline.py` ends with a step, on by default and skipped with `--no-entries`, that writes three hypothetical setups with entry, stop and target (`prompts/trade_entries.schema.json`). By default `trade_entries.py build` computes the whole file with no Claude call; with `--entries-by-claude` the step instead sends `prompts/trade_entries.md` (filled by `trade_entries.py prompt`) to a second `claude -p` call with no tools, run outside the repo, so that Claude writes the sentences. The rules are mechanical (prices from zone edges, odds from `reach`/`turn`), and `trade_entries.py` implements the same rules in code: `build` writes and `check` recomputes every number, so **the template's rules and `setups()`/`pick()` must change together** (and a new free-text field needs wording in every `TEXT` language), and the JSON example at the end of the template must keep passing `check` against `examples/` (a test pins this). The precision rule (round prices to the candle rows' decimals, discard a zero risk, the "no setup passes" error) is stated in the template too. A failed check exits 1 but leaves the input, projection and chart in place. The step reads the projection's `supports`/`resistances` (`zone`, `reach`, `turn`), `structure.volatility.assumed`, `horizon.closes`/`last`, `events` and `confidence`, so a change to those fields in `SKILL.md` needs a matching change here. The skill and the chart themselves still emit no stops or targets, and the setups carry no position size and never raise the confidence level.

The output is analysis, not advice: the skill never emits buy/sell/hold calls, stops, targets or position sizes, and `confidence.level` is only ever `low` or `medium`. The probabilities of a projection are not backtested: `backtest.py` checks only the unadjusted baseline on mechanical zones, and its report keeps the caveats saying so. `value_test.py` compares Claude's adjusted numbers with that baseline on dates after the model's training cutoff; its result (README, "Does Claude's adjustment help?") is a small sample. Preserve these constraints and the disclaimers when editing the skill, the chart footer or the README.
