# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A three-step pipeline that turns price candles into support/resistance zones with probabilities and plots them. Each step exchanges plain JSON:

```
build_prompt.py  ──input.json──►  reversal-zones-projection skill (Claude)  ──projection.json──►  plot_projection.py
```

`README.md` is the full user-facing reference (CLI options, both JSON formats, glossary, known limits, roadmap). Keep it in sync when changing a CLI flag or a JSON field.

## Commands

```bash
uv sync                                                                      # Python 3.12+ (.python-version); also installs the `zones` command
uv run zones PETR4.SA --horizon 1-3m                                         # all steps: Yahoo, headless `claude -p`, rz.py check, chart, trade setups (--no-entries to skip), into runs/TICKER/TIME_HORIZON/
uv run zones PETR4.SA --engine mechanical                                    # step 2 by mechanical.py: no Claude call, free, ~1 s
uv run python mechanical.py input.json -o projection.json                    # step 2 alone, mechanical
uv run python run_pipeline.py PETR4.SA --horizon 1-3m                        # the same thing; `zones` is run_pipeline.main
uv run zones list [TICKER]                                                   # saved projections (rz.py list); `zones runs [TICKER]`: the folders under ./runs
uv run zones score [TICKER | FOLDER] [--json]                                # score_projections.py, hits Yahoo Finance
uv run zones score-entries [TICKER | FOLDER] [--runs [DIR]] [--optimistic] [--json]   # score_entries.py: saved entries.json vs later prices, hits Yahoo
uv run zones backtest TICKER... [backtest.py options]                       # backtest.py, hits Yahoo Finance
uv run zones plot WHAT [-o FILE] [plot options]                              # plot_projection.py for a run; WHAT: a folder with the pair, or a ticker (latest run, else latest saved)
uv run zones show WHAT                                                       # show_run.py; `zones entries WHAT`: trade_entries.py build, then check
uv tool install --editable .                                                 # optional: `zones` in any directory, still running this checkout
uv run zones --show-config                                                   # config files found, every setting and where its value comes from (--init-config writes a template, --no-config ignores the files)
uv run python build_prompt.py PETR4.SA --horizon 1-3m -o petr4_input.json    # step 1, hits Yahoo Finance
uv run python plot_projection.py petr4_input.json petr4_projection.json -o petr4.png   # step 3
uv run python show_run.py FOLDER | INPUT.json PROJECTION.json [ENTRIES.json]   # one run as a text summary (what `zones` prints before the file paths)
uv run python score_projections.py [FOLDER] [--ticker T] [--json]            # saved projections vs later prices, hits Yahoo Finance
uv run python backtest.py PETR4.SA NVDA --horizon 1-3m [--method 1] [--json] [--csv F]   # baseline probabilities on past dates, hits Yahoo, no Claude (also `zones backtest`)
uv run python backtest_entries.py T... --horizon 1-2w 1-3m [--optimistic] [--json] [--csv F]   # the trade setups on past dates (mechanical engine), hits Yahoo, no Claude (also `zones backtest-entries`)
uv run python backtest_entries.py --universe backtest_universe.txt --horizon 1-2w 1-3m 6-12m --start 2005-01-03 --by-year --by-regime --by-part --subset original --jobs 10   # the long run, ~1 h
uv run python value_test.py T... --out DIR [--max-cost USD] [--jobs N]          # PAID: Claude's adjustment vs the baseline on dates after the model's training cutoff; resumes in DIR
uv run zones batch watchlist.txt --jobs 2 --max-cost 5 [pipeline options]    # one pipeline run per ticker, summary.csv in runs/batch/TIME/
uv run zones cache [info|clear|path] [TICKER...]                             # the candle cache (data_source.py); --no-cache on build_prompt/backtest/score skips it
uv run python build_prompt.py PETR4.SA --prices data/petr4.csv               # step 1 from CSV files, no network
uv run pytest                                                                # all tests, offline, a few seconds
uv run pytest tests/test_rz.py::test_sim_output_structure                    # a single test
```

The tests in `tests/` never touch the network: they cover the pure functions of `build_prompt.py`, `rz.py`, a plot smoke test, `run_pipeline.py` with Yahoo and Claude stubbed (its config files in `tests/test_config.py`), `score_projections.py`, `score_entries.py` (`tests/test_score_entries.py`: a temp history with hand-made setups and candles, results equal to `backtest_entries.walk()`), `backtest.py` and `backtest_entries.py` with Yahoo stubbed (the setup walk on hand-made candles with known fills, gaps and same-candle ambiguity in `tests/test_backtest_entries.py`, which also covers the universe file, the history skip, the period and regime tables and `--jobs` against a serial run, with real spawned processes), `value_test.py` with Yahoo and its `launch()` stubbed, `batch_runs.py` (fake child runs, plus the real pipeline in the child with Yahoo and `claude` stubbed), `data_source.py` (`tests/test_data_source.py`: retries with simulated 429/5xx/hung requests, the cross-process rate limit with real child processes, row checks, the cache against a fake Yahoo, CSV import), the live output of `build_prompt.py` byte for byte with a fake Yahoo and a frozen clock (`tests/test_build_prompt_live.py`, expected files in `tests/fixtures/build_prompt_live/`; regenerate them only for a deliberate output change), and the cross-file contracts below (`tests/test_contracts.py`). `tests/fixtures/input.json` is synthetic; regenerate it with `uv run python tests/fixtures/make_input.py`. `tests/conftest.py` gives every test an empty candle cache of its own (`ZONES_CACHE_DIR`, inherited by child processes), no rate-limit spacing and a no-op `data_source.sleep`, so no test touches `~/.cache/zones` or waits; `run_cli()` in the live test makes its own temp cache too, also when run as a script to regenerate the expected files. There is no linter or CI, and nothing tests the Yahoo download itself, so still run the scripts end to end after changing them.

No test may read the developer's own config file: the autouse `no_real_config` fixture in `tests/conftest.py` points `ZONES_CONFIG` at a file that does not exist, turns the `./zones.toml` lookup off (`run_pipeline.PROJECT_CONFIG = None`) and puts `RZ_PROJECTIONS_DIR` back after each test. A test about config files sets `ZONES_CONFIG` to its own temp file (and `PROJECT_CONFIG` back to `"zones.toml"` after a `chdir` to a temp folder). When checking by hand, set `ZONES_CONFIG` (or `HOME`/`XDG_CONFIG_HOME`) to a temp path; never write to the real `~/.config`.

Step 2 is the `reversal-zones-projection` project skill: given an input JSON, Claude follows `.claude/skills/reversal-zones-projection/SKILL.md`. Its helper can also be run directly:

```bash
RZ=.claude/skills/reversal-zones-projection/scripts/rz.py
uv run python $RZ levels input.json              # facts for choosing zones
uv run python $RZ sim    input.json zones.json [--method 1]   # baseline probabilities (default: the newest sim method)
uv run python $RZ check  output.json             # validate a projection; prints OK or the violations
uv run python $RZ save   input.json output.json  # keep the pair under projections/TICKER/TIME_HORIZON/
uv run python $RZ list                           # saved projections, oldest first, open or ended
uv run python $RZ score  input.json output.json candles.json   # outcome of one projection from a candles file, offline
```

Use `rz.py check` on any projection JSON you write or edit by hand.

The skill saves every projection by default (`rz.py save`, its last workflow step) so past projections can be scored later. `projections/` is gitignored, relative to the working directory (override with `RZ_PROJECTIONS_DIR` or a trailing folder argument), and append-only: `save` never overwrites and nothing should edit or delete an earlier entry.

`examples/` holds a ready-made input/projection pair (`petr4_input.json`, `petr4_projection.json`) for trying `plot_projection.py` and `rz.py check` without Yahoo or step 2.

## Architecture

- **`build_prompt.py`** (step 1): `PRESETS` maps each horizon to a main series, an optional coarser context series, the `close_basis` and the probability meaning. The context series is filtered to candles that start *before* the main series, so the two never overlap. `render()` uses placeholder substitution to keep each candle row and event on one line inside otherwise indented JSON. Only `build()`, `history()` and `upcoming_events()` touch Yahoo, and all three through `data_source` (the probe with `fetch()`, never cached; the series with `candles()`; the calendar with `throttle()` and `call()`); `make_series()`, `make_all_series(args, candles_of, ...)` (the series of a horizon, from a function that returns the candles of one preset entry) and `assemble()` (the JSON from its parts) are offline, so `backtest.py` builds past inputs with the same code. `build()` stamps `schema_version` (`SCHEMA_VERSION`) and a `provenance` block (`provenance()`: source, library version, UTC download time, `auto_adjust: false`, per series rows/first/last/what was requested, and `data_sha256` = `data_hash(data)`, the sha256 of `data` in canonical JSON). `provenance()` reads everything from the finished prompt, so another way of building an input (e.g. from stored candles) can call it with its own `source`. `details` adds per series what `data_source` reported (`series_details()`: `checks`, `cache`, `note`, `built_from`), only when there is something, so a clean fresh download adds no key. `--prices` goes to `build_from_files()`: `data_source.load_prices()`, periods counted from each series' newest row, session `unsure`, events from `--event` only, and `provenance(..., auto_adjust=None, files=...)` (`files` with sha256, `read_at`, `adjustment`).
- **`.claude/skills/reversal-zones-projection/`** (step 2): `SKILL.md` is the prompt that defines the workflow, the zone-selection rules, the limits on adjusting simulated probabilities and the exact output schema. `scripts/rz.py` is its helper (Monte Carlo with a fixed seed, so the same input and zones give the same baseline).
- **`data_source.py`** (every price request): `fetch()` is one `history()` call with `throttle()` (cross-process spacing via a `fcntl`/`msvcrt`-locked `yahoo.next` in the cache folder), a per-attempt deadline (`call()`: one reused worker thread, because yfinance's session redoes a ~5 s handshake on each new thread), and retries by `classify()`: `rate_limited`/`transient` are retried with `backoff()` (exponential, capped, jitter) within `ATTEMPTS`/`BUDGET`, then `DataError`; `missing` (unknown symbol, Yahoo's explicit "no data") becomes an empty frame so each caller keeps its own message; `other` is raised. It sets `yfinance.config.debug.hide_exceptions = False` so failures are exceptions, not empty frames. `timeout=` is passed only to a `history()` that names it, so test fakes with fixed or `**kwargs` signatures get exactly the keywords they always got. `validate()` drops/fixes/flags rows and returns `checks`. `candles()` = fetch + validate + the cache: only finished `1d`/`1wk`/`1mo` candles (ended at least `GRACE` ago) are stored, per key symbol/interval/adjustment/actions; a covered request fetches from the `OVERLAP`-th newest cached row, requires those rows to match (else full download and a `note`), and takes everything newer from the fresh answer. `load_prices()`/`Prices` read CSV files (`read_csv()`, `find_files()`, `resample()` for weekly/monthly from daily). `main()` is `zones cache`. It imports nothing from the other scripts; they import it (plain `import data_source`, the root is on `sys.path` for every script).
- **`score_projections.py`** (after the fact): reads each saved folder's optional `provenance.json` (`made_by()`) to name the model and rules per projection, and `by_model()` adds a Brier score per model to the calibration (no file: `unrecorded`). It walks the saved history with `rz.saved()`, downloads daily candles once per ticker (`download()`, the only function that touches Yahoo, through `data_source.candles(actions=True)`, splits from its report; tests stub it; `CACHE`/`--no-cache`), builds weekly/monthly candles from them (`aggregate()`), and calls `rz.outcome()` per projection. `calibration()` buckets the forecasts of ended projections and computes Brier scores. It loads `rz.py` by path, like the plot.
- **`backtest.py`** (baseline on past dates): `download()` is the only function that touches Yahoo (tests stub it): daily candles once per ticker, through `data_source.candles()` (`CACHE`/`--no-cache`; the returned dict gains `data` with the checks and cache report). `input_as_of()` slices them at the as-of day *before* anything else and builds the input with `build_prompt.make_all_series()`/`assemble()`, weekly/monthly candles from `score_projections.aggregate()`. `choose_zones()` is the one place the mechanical zone rule lives (`RULE` describes it; README repeats it; its parameters `WIDTH_FACTOR` 1.5 and `MIN_MEMBERS` 2 since setup rules 6, chosen for the setups by the study in `examples/zone_rule_2026-11-21/`, README "A stronger zone rule"), reading `rz.facts()`. Then `rz.baseline()` and `rz.outcome()`, and the summary reuses `score_projections.calibration()`, `brier()` and `buckets()`. `DEFAULT_PATHS` is read from `rz.baseline`'s signature. `tests/test_backtest.py` pins no look-ahead (the input from all candles equals the input from candles cut at the as-of day).
- **Outcome definitions live in `rz.py`**, not in the scorer: `reached()` and `middles()` are the single implementation of "reached", "broken" and the scenario lines, used by `sim()` on 200,000 simulated paths and by `outcome()` on the one realised path. `realised()` picks the horizon's candles and mirrors `schedule()`. `tests/test_rz_outcome.py` feeds `walk()`'s simulated paths to `outcome()` as candles and requires the frequencies to reproduce `sim()`; change one side only with that test green. `walk()` must keep drawing the same random numbers in the same order (baselines are reproducible); drift is a deterministic term (`drift_steps()`) added after all draws, so `test_drift_does_not_change_the_random_draws` holds. `levels`/`sim` print what `facts()`/`baseline()` return; `unpack()` is `load()` for a dict already read. Code that needs the numbers calls those, not the printing commands.
- **`mechanical.py`** (step 2 without Claude, `--engine mechanical`): `build()` turns an input into a complete projection in SKILL.md's schema: zones from `backtest.clustered_zones()` on `rz.facts()` (the rule lives only in backtest.py; `choose_zones()` is `clustered_zones()` without the members, and the members are what the evidence strings name), probabilities from `rz.baseline()` (default sim method, no shocks) copied verbatim through `backtest.projection()`, strength by `strength()`, input events passed through unsimulated, `drivers: []`, confidence always `low`. Free text from `TEXT` (en, pt; one entry per language, like trade_entries.py; scenario bounds keep sim's dot-decimal numbers, which the plot's regex reads). `render()` has fixed formatting: same input, same bytes. It imports backtest.py (and through it pandas, build_prompt, score_projections); that is fine, backtest.py does no network at import. `build()` refuses to return a projection that fails `rz.problems()`. `build(d, method=None)` takes the sim method only so that `backtest_entries.py --method` can pass it; `None` is the default a live run uses.
- **`backtest_entries.py`** (the trade setups on past dates): per horizon, ticker and as-of date of backtest.py's grid (`backtest.default_range()`, `DEFAULT_STEP`, `as_of_days()`, `download()`), `run_case()` makes exactly what a live `zones --engine mechanical` run makes: `backtest.input_as_of()`, `mechanical.build()`, `trade_entries.build()`. `walk()` plays one setup on the daily candles after the as-of day up to `valid_until` (daily whatever the close basis): limit and stop fills on touch, a gap past the entry fills at the open, market orders at the next open, exits at the stop/target price or at an open past them (below -1R possible), expiry at the last close; inside a candle, a level the price must have crossed after the entry counts as after the fill, anything else is ambiguous and resolved against the setup unless `optimistic`. Every setup is walked both ways (`ambiguous`, `r_other`). `stats()`/`scope()` compare stated `fill`, `win_if_filled`, `if_filled` and `per_order` with the observed rates and mean R, by side, kind, order, quality, rank and ticker, with `sp.brier()`/`sp.buckets()`, a case bootstrap (`bootstrap()`, fixed seed; it packs each case once but adds the same numbers in the same order as resampling the setups, `test_bootstrap_is_the_original_computation`) and the per-ticker spread. `RULES` and `CAVEATS` are printed with every report. The long run: `run_case()` first skips a date whose daily rows start after `history_start()` (the first day of the horizon's longest preset series, `longest_period()`), so a young listing never gets shorter series than a live run of a mature one; `read_universe()` reads `backtest_universe.txt` (versioned, `[group] reason` lines, `TICKER@FIRST..LAST` ranges applied by `cut()`; the `original` group is the twelve tickers of every earlier report and stays uncut); `--jobs N` sends chunks of `CHUNK` as-of dates to a spawn `ProcessPoolExecutor` running the top-level `cases()`, while downloads stay in the main process (data_source's cache and rate limit) and `collect()` appends results in submission order, so the output equals a serial run byte for byte (`test_parallel_run_is_identical_to_serial`; nothing that depends on `jobs` may enter the settings or the summary); `part_of()` labels every case with the fixed fit / held-out split (`HELD_OUT_YEARS`, `PARTS`), `label_regimes()` with its index's (`index_of()`) trailing return (`REGIME_BAND`, `TRAILING_DAYS`) and later move; `summarise(..., periods, groups, subsets, part)` adds the compact tables (`compact()`, `split()`, `PERIOD_KEYS`, `TABLES`) only when asked, so the default report is unchanged (the committed `examples/backtest_entries_2026-11-19_rules3.txt` was reproduced byte for byte with `--jobs 10`).
- **`score_entries.py`** (`zones score-entries`, the saved setups after the fact): walks the saved history with `rz.saved()` (and with `--runs [DIR]` the run folders too; a file whose sha256 was already seen is a copy and counted once, the history's first), reads `entries.json` beside each projection (`read_entries()`: missing -> `without_entries`, a count; unreadable, the `error` reply or damaged -> `not_scored` with the reason), and plays every entry with `backtest_entries.setup_of()` and `walk()` on the daily candles after the as-of day up to `valid_until`, both orderings (default pessimistic, `--optimistic`). Downloads are `score_projections.Prices`/`download()` (so `data_source.candles()`, `sp.CACHE`/`--no-cache`), one per ticker; a split after the as-of day and `sp.check_scale()` failures are not scored; candles are rounded to `trade_entries.places()` of the input. `valid_until` before the exchange's today (`sp.today_in()`) means ended; an open setup's `expiry` is renamed `open` (provisional). The summary takes ended setups only, one `backtest_entries.scope()` per rules version (`reply.get("rules", 1)`, never pooled) plus `by_horizon` and `by_author` (`entries_made_by()`: the `entries` block of `provenance.json`, `computed`/`claude`/`unrecorded`). It imports `trade_entries.py` only for `places()` and `RULES`. `RULES` (its own first and last items around `backtest_entries.RULES[1:]`) and `CAVEATS` are printed with every report.
- **`plot_projection.py`** (step 3): one `build()` function that draws five matplotlib axes (candles + zones, probability bars sharing the price axis, scenario bar, notes, side panel). `THEMES` and `TEXT` hold all colours and translated strings, including each language's number separators and intraday tick format. Labels are placed by measuring text with the figure's renderer (`extent()`, `spread()`, `share_lines()`), not by fixed offsets; `tests/test_plot_layout.py` pins that with text boxes, never pixels.
- **`trade_entries.py`** (trade setups): `setups(source, proj)` and `pick()` are the template's rules in code (rules version `RULES` = 6, written into every reply; `problems()` names a file without it as written by version 1 instead of listing every number, and a rules 2, 3 or 5 file as an earlier version through `EARLIER`: version 2 swapped in the other side and used one ±0.05 R quality band, version 3 stated the uncorrected path counts, version 5 priced the setups on the earlier zone rule's zones with a correction fitted on them; 4 was the GARCH candidate, never shipped). The odds are counted on simulated paths: `paths()` loads rz.py by path (`RZ_PATH`, like the plot), runs `rz.walk()` with the default sim method's drift and no shocks for the first `PATHS` (20,000) paths, fills in the trading days between two closes with a Brownian bridge and draws each day's high and low as Brownian-bridge extremes scaled by `SPREAD` (0.65, chosen on the first two years of the setup backtest), both from their own generator (`BRIDGE_SEED`), so walk()'s draws and every rz.py output stay untouched; `odds()` plays one setup on those days by `backtest_entries.walk()`'s pessimistic rules, and `corrected()` (called in `setups()` after `odds()` and the `MIN_FILL` test, before ranking) applies `CORRECTION`: per (horizon, side, kind), log-odds shifts of fill (not a market order's) and win and an R shift of the edge, fitted on the fit part of the long setup backtest over every valid setup and adopted at `1-2w` and `1-3m` only (README, "An empirical correction of the odds, per horizon, side and kind"); `detail.corrected` says when it applied, and `build()` then words `basis`, `method` and one limit accordingly. `quality` is `quality(if_filled, band(source))`: `EDGE_BAND` maps the input's `horizon` to the model's measured error there (the larger of |stated - observed| mean R per fill of the picks under either ordering, fit years; the widest band for a horizon without a backtest), and an edge inside it is `marginal`, "cannot be told from zero"; `build()` states the band in `confidence.limits` (`TEXT[*]["quality"]`). `PATHS`, `BRIDGE_SEED`, `DAYS`, `SPREAD`, `CORRECTION`, `EDGE_BAND` (quality) and `MIN_FILL` (a setup filling on fewer than 5% of the paths is discarded) are part of the rules: changing one means a new `RULES` number, the template, its example and the README's backtest. `candidates()` is every valid setup with its numbers, which `fill()` puts in the prompt (`{{SETUPS_JSON}}`) because Claude has no tools to count paths. Prices (stop, risk, reward, units) are rounded to `places(source)`, the precision of the input's candle rows (at least 2), and `problems()` compares prices to that precision (`price_tolerance()`), the rest to 0.011; a setup whose risk rounds to zero is discarded, and an error reply is accepted when the files are unusable or no setup passes; `build()` turns them into the whole reply, writing its sentences from `TEXT` (one entry per language, like the chart's), so the default path needs no Claude; `fill()` builds the prompt from `prompts/trade_entries.md` for `--entries-by-claude`; `problems()` checks a reply, computed or Claude's, against the schema and those rules. See Domain constraint.
- **`run_pipeline.py`** (all steps): a thin orchestrator that shares no code with the others. It runs the two scripts and `rz.py check` as subprocesses and step 2 as `claude -p` (`claude_command()` holds the exact flags and the tool allowlist, `call_claude()` is the only place that starts Claude). Step 2 asks for `--output-format stream-json --verbose` (one JSON event per line): `call_claude()` drains stdout and stderr in two threads and enforces the timeout itself, `Progress` maps tool calls to the skill's stages (`STAGES`, one stderr line each, heartbeat after a silence, nothing with `--quiet`) and skips every event or line it does not know, and `claude_result()` finds the final `result` event, from which `summary()` prints duration, turns and cost (a field Claude Code does not report is left out, never guessed). A new helper subcommand or work-file name in the skill needs a matching entry in `STAGES`/`Progress.stage()` to show up. Options it does not declare go to `build_prompt.py` untouched, so a new step-1 flag needs no change here; plot options are forwarded only when given, so step 3 keeps its own defaults. Output: without `--out-dir`, `run_folder()` makes a new `runs/TICKER/TIME_HORIZON/` under the current directory (named like `rz.py save` names its folders, from the input's `asset.ticker`, `now.time` and `horizon`, with `_2`, `_3` ... when taken) holding `input.json`, `projection.json` and `chart.png`, with files given by `--input`/`--projection` copied in so every folder is complete; plotting again with `--chart` makes no folder. With `--out-dir` the files go exactly there as `STEM_*` (stem from the ticker or `--name`) and given files are not copied. Nothing is created before the input and the given projection have loaded, and `build_prompt.py` writes into a throwaway folder. `runs/` is disposable output; `projections/` stays the append-only record, and the two are never merged. `--open` calls `open_chart()` after a successful run (`start_viewer()` is the only place that starts a viewer; failure is one warning). When the input's `research` is not `none` its prompt (`claude_prompt()`) restates in two lines the skill's research rule (every driver `source` and event size comes from a page opened with WebFetch) and names the tools; the rule itself lives in `SKILL.md`, because drivers written from the search summary alone did not match their sources in real runs. `--engine` (setting `engine`, default `claude`, choices `ENGINES`) picks step 2: `mechanical` runs `mechanical.py` as a subprocess (`mechanical_project()`), never Claude, appends `--research=none` to the step-1 arguments (one `research_warning()` when a research level was typed or came from a config file, or when a given `--input` asks for research), prints `made in X s · no Claude Code call · $0` (deliberately not `done in M:SS`, which batch_runs.py's `CLAUDE_END` reads as a Claude call), and writes provenance with `made_by: "mechanical"`, a `mechanical` block instead of `claude`, and `rules_provenance("mechanical")` over `MECHANICAL_RULE_FILES` (no SKILL.md; mechanical.py and backtest.py). score_projections.py groups those as model `mechanical`; show_run.py says "Made by the mechanical engine". It tells Claude to skip the skill's save step and runs `rz.py save` itself after `check` (not with `--projection` or `--no-save`), so each run is kept exactly once; a failed save only warns. Provenance (section `# ---- provenance` in `run_pipeline.py`): `project()` returns `claude_facts()` of the stream (model and `claude_code_version` from the `system` init event, turns/cost/durations/usage from the `result` event, `modelUsage` keys as `models_used`; absent fields stay absent), and after `check`/`save` `run_provenance()` writes `provenance.json` (`STEM_provenance.json` with `--out-dir`) into the run folder and the saved folder: input/projection sha256, the input's own `provenance`, both `schema_version`s, the Claude facts, and `rules_provenance()` (sha256 of every `RULE_FILES` entry, a 12-hex `version` over them, git commit and dirty flag via `git_state()`). The entries step adds an `entries` block and rewrites both copies in the same run. A run with `--projection` writes none (it copies a sibling provenance into a new run folder, never overwrites one). A new rule file belongs in `RULE_FILES`. The tests stub `run` (for Yahoo) and `call_claude` (or replace the `claude` binary with a script that replays `tests/fixtures/claude_stream.jsonl`, a cut-down recording of one real run), and point `RZ_PROJECTIONS_DIR` at a temp folder so they never write into the repo's `projections/`. Personal defaults: `parse()` ends in `configured()`, which reads the user file (`user_config()`: `$ZONES_CONFIG`, else `$XDG_CONFIG_HOME/zones/config.toml`, else `~/.config/zones/config.toml`) and `./zones.toml`, and `settle()` is the single implementation of the precedence command line > environment variable (`RZ_PROJECTIONS_DIR` for `history_dir`, `ZONES_CACHE_DIR` for `cache_dir`) > project file > user file > built-in default (documented once, in README "Your defaults"). `SETTINGS` lists what a file may set; a key is the option's name with underscores. Own options have `None` as their argparse default so that "typed" can be told from "default", and `configured()` fills `args` with the settled values (`args.no_entries`/`args.no_save` are derived from `entries`/`save`, and switches are `BooleanOptionalAction`, so each has a `--no-` form), which is why `pipeline()` needed no change beyond `args.runs_dir`. Step-1 settings are the exception to "a new step-1 flag needs no change here": `SETTINGS` repeats their names, choices and defaults (and the chart's themes and languages) so that a bad config value fails before any download or Claude call; `tests/test_config.py` compares them with `build_prompt.arguments()` and `plot_projection.THEMES`/`TEXT`, and a step-1 flag that is not in `SETTINGS` still passes through from the command line, it just cannot be set in a file. `step1_arguments()` turns file values into `--opt=value` arguments placed *before* the user's own, only for options not typed in this run (`typed()` sees `--opt value`, `--opt=value` and abbreviations) and never with `--input`; `--no-volume` is declared here because `build_prompt.py` has no off form. `history_dir` from a file or `--history-dir` is exported as `RZ_PROJECTIONS_DIR` for the whole process in `configured()`, never over a variable that is already set by the user; `cache_dir`/`--cache-dir` likewise as `ZONES_CACHE_DIR` (`export_cache_dir()`, also from `command_config()`), the only way the child scripts learn it. Paths in a file are resolved against the file's folder (`config_path()`). Config problems are a `PipelineError` that `parse()` prints as one `Error:` line before exiting 1; `--show-config` and `--init-config` exit from `parse()` too, so `main()` is untouched. A test that runs `main()` without `--out-dir` must first `chdir` to a temp folder (the autouse fixture in `tests/test_run_pipeline_outputs.py`), or it writes `runs/` into the repo, and must stub `start_viewer` before passing `--open`.
- **`value_test.py`** (does the paid step 2 beat the free baseline?): Each case's baseline uses the sim method that run's step 2 saw (`made_with()`: `rules.sim_method` of its provenance, else 1, since runs before numbered methods all used method 1), or the drift of method 2 would show up as an adjustment Claude never made. imports `backtest.py` and changes nothing in it. Per (ticker, as-of date) it writes `OUT/cases/TICKER/DATE/input.json` with `backtest.input_as_of()` (research none, no events), runs the real pipeline on it (`pipeline_command()`: `run_pipeline.py --no-config --input ... --no-entries --no-save --model M --out-dir CASE --name case`; `launch()` is the only place that starts it, and `tests/conftest.py`'s `no_real_claude` replaces it with a function that raises), then scores three versions with `rz.outcome()`: Claude's projection, `rz.baseline()` on Claude's own zone edges (`bt.projection()`), and `bt.run_case()` (mechanical zones). Cost comes from `case_provenance.json` (`total_cost_usd`), else the `$` on the pipeline's summary line; a run that never reached Claude (no `[2/` header) costs 0 and writes `not_started.json` instead of `run.json`, so it is retried. `run.json` means paid: a resumed `--out` never launches that case again, failed or not. `Budget` starts a run only while spent + (runs in flight + 1) x reserve <= `--max-cost` (reserve = highest cost seen, `FIRST_RESERVE` before any). Look-ahead: `TRAINING_CUTOFF` (model id -> month, only from Anthropic's models overview, `CUTOFF_SOURCE`) refuses a `--start` on or before the cutoff, and `score_case()` drops a run whose reported model is unknown there or too recent. Candles are cached in `OUT/data/` so a resume scores the same prices. Tests: `tests/test_value_test.py` (stubbed Yahoo and a fake `launch` that writes the files the pipeline would).
- **`run_pipeline.py`, the commands after a run**: `main()` starts with `dispatch()`, which runs `zones list|runs|score|score-entries|plot|show|entries|backtest|backtest-entries|batch|cache` (`COMMANDS`, one function each) and otherwise hands the arguments to `parse()` unchanged. A first argument is a command only when it is exactly one of those lowercase words, so `zones nvda`, `zones LIST`, `--input` and `--help` stay the pipeline's; `run` and `--` are stripped and force the pipeline (`zones run list`). The commands are as thin as the pipeline: `relay()` runs a script on the user's terminal and returns its exit code (`score_projections.py`, `score_entries.py`, `plot_projection.py`, `show_run.py`, `backtest.py` with every argument passed on), `run()` captures where the output is filtered or checked (`rz.py list`, which has no ticker filter, and `trade_entries.py build` then `check` into a temp file). Options a command does not declare are passed on, which is why WHAT must come first (`what_first()`): a later word may be an option's value. `resolve()` turns WHAT into one run: a folder holding the pair (`pair()`: plain names, or one `STEM_` pair, `--name` to pick), a folder with such folders below it, or a ticker, looked up case-insensitively in `./runs` first and then in the history (`history()`: `$RZ_PROJECTIONS_DIR`, else `./projections`), latest by folder name (`folder_key()`: time, then `_N`; `FOLDER_NAME` must keep matching what `run_folder()` and `rz.py save` produce), narrowed by `--horizon`. `target()` decides where `plot` and `entries` write: beside the pair for a run (replacing `chart.png`/`entries.json`), the current directory for a saved projection, and never inside the history (`kept()`), `-o` included. `runs` reads folder names only. Before a command runs, `command_config()` reads the same config files as `configured()` and applies `runs_dir` (as `runs_home`), `history_dir` (exported, never over a set `RZ_PROJECTIONS_DIR`) and the chart settings (`chart_config`: `plot` gets theme/lang/candles/dpi/open, `show` gets lang, each only when not typed, via `configured_options()`); a bad file is the same one-line error. Tests: `tests/test_zones_commands.py` (stub `relay` for `score`; copy its autouse `cwd` and `store` fixtures).
- **`show_run.py`** (the summary `zones` ends with): `summary()` turns an input, a projection and optionally an entries file into lines of `(text, style)` segments, top to bottom like the chart; `table()` folds columns that do not fit into a second block instead of cutting them, and `render()` clips every line to the width and adds ANSI codes only when asked. It adds no words of its own beyond the labels in its `TEXT` (one entry per language; the keys it shares with the chart, the number separators and `price_digits()` are copies of `plot_projection.py`'s, which it must not import because of matplotlib, and `tests/test_show_run.py` pins them equal). Only what the plot's validation requires is required (`required()`); a malformed optional section is skipped. `run_pipeline.py` runs it as a subprocess after a successful run (`show_summary()`, off with `--no-summary`, any failure is one warning) and relays the output before the file paths; because the script then writes into a pipe, the pipeline passes `--color --width N` when its own stdout is a terminal and `--no-color` otherwise, and `NO_COLOR` always wins. See Domain constraint: no label may read as advice, and the setups keep the note of their own file.

- **`batch_runs.py`** (`zones batch`): the pipeline over a watchlist. `run_pipeline.batch()` imports it and calls `main()` in-process (not relayed, so Ctrl-C reaches its loop and the summary is still written); it imports `run_pipeline` for small helpers and `command_config()` (to find `runs_dir`). Each ticker is a child process `run_pipeline.py run TICKER [options]` (`child_command()`, `PIPELINE`), with stdout and stderr into `RUNS_DIR/batch/TIME/logs/TICKER.log`; `Batch.run()` is a polling loop (no threads) that starts up to `--jobs` children, stops starting new ones once the reported costs reach `--max-cost`, and rewrites `summary.csv` after every run. It duplicates no pipeline logic: it reads what the run printed (see the contract below) and the run folder's `projection.json`. The batch folder name has no `_HORIZON`, so `FOLDER_NAME` and `zones runs` do not take it for a run. `--prices` is passed on like any option; one CSV *file* with several tickers is refused. The children share Yahoo's rate limit and the candle cache through `ZONES_CACHE_DIR`.

### Contracts that span files

The three pieces share no code, only JSON conventions. Changing one side silently breaks another:

- **Data layer.** Every Yahoo request goes through `data_source.py`; a new download must too (`fetch()` or `candles()`), or it escapes the retries, the shared rate limit and the row checks. The cache must never serve an unfinished candle: `finished()` decides, and the newest candles always come from the fresh request. `provenance.series[*].checks|cache|note|built_from` and the CSV keys (`files`, `read_at`, `adjustment`) are written by `build_prompt.py` from `data_source`'s reports; README "Data sources" documents them, the retry policy, the cache rules and the CSV format, so change them together.
- **Backtest and step 1 share the input builder.** A change to `PRESETS`, `make_all_series()` or `assemble()` changes past inputs in `backtest.py` too; a change to `rz.levels` output keys (`typical_zone_width`, `pivot_*`, `recent_*`, `retracements`, `swing`) needs `choose_zones()` to follow. `backtest.py` supports the daily-or-coarser horizons only (`HORIZONS`); a new one needs an entry in `DEFAULT_STEP`.
- **Main series selection** is implemented twice, identically: the series whose `candles` equals `close_basis`, falling back to the last series (`load()` in `rz.py`, `build()` in `plot_projection.py`). `build_prompt.py` guarantees this by inserting the context series *first*.
- **Horizon and candle labels**: adding a horizon or interval means touching `PRESETS`/`LABEL` in `build_prompt.py`, `HORIZON_DAYS`/`CANDLE_DAYS`/`schedule()` in `rz.py`, the horizon tables in `SKILL.md`, and `TEXT[*]["labels"]` in `plot_projection.py`.
- **`last_row: "forming"`** shortens the first simulation step in `rz.py` and removes one future slot in the plot.
- **Validation**: `plot_projection.py` `preflight()` runs before `build()` and reports every problem at once (exit 1, no traceback). `validate()` covers what `build()` reads, so a new `[...]` access in `build()` needs a matching check there. The projection's rules are not duplicated: the plot loads `rz.py` by path (`RZ_PATH`) and calls `problems(proj, complete=False)`; `rz.py check`/`save` call the same function with `complete=True`. Rule violations block the plot unless `--no-check`; without `rz.py` the plot checks structure only and says so.
- **The mechanical engine** shares the zone rule with backtest.py (`clustered_zones()`; changing it changes both, backtest.py's evaluation results, every setup's prices and so the fitted `CORRECTION` and `EDGE_BAND`: a zone-rule change is a new `RULES` number, refitted and judged like rules 6 was) and the output schema with SKILL.md: a new or renamed key, id or key order in SKILL.md's schema needs the same change in `mechanical.build()`, and `tests/test_mechanical.py` pins key order, `rz.py check`, byte-identical output, zones equal to `choose_zones()` and probabilities equal to `rz.baseline()`. A new step-2 field that trade_entries.py reads must be filled there too.
- **The setup backtest** (`backtest_entries.py`) reuses `backtest.input_as_of()`, `mechanical.build()` and `trade_entries.build()` and has no rule of its own for zones, odds or setups, so a change to the zone rule, the sim method default, `setups()`/`pick()` or the template's rules changes its results: rerun it and update the README's "Backtest of the trade setups" table when one of those changes. A free parameter of the setup rules was chosen on the first two years of as-of dates only (cases whose `valid_until` falls before the third year) and reported on the third year, as `SPREAD` and `EDGE_BAND` were; since rules 5 a parameter is fitted on the fit part of the long run (`--universe backtest_universe.txt`, `--part fit`, `HELD_OUT_YEARS`) and judged once on `--part held-out` by a criterion written into the README beforehand, as `CORRECTION` was. From now on a rule or parameter change (drift, volatility, odds, ranking) is fitted on the `fit` part of the long run (`--universe backtest_universe.txt --start 2005-01-03 --part fit`) and judged once on `--part held-out` (README "The fit / held-out split"); `HELD_OUT_YEARS` never changes, and a new universe gets a new `version:` line, named with every result. Its walk reads the reply's `entries[*].entry.order/price`, `stop.price`, `target.price`, `payoff.risk`, `odds`, `edge`, `quality` and `valid_until`; a schema change there needs `setup_of()` to follow.
- **The setup scorer** (`score_entries.py`) has no walk of its own: it calls `backtest_entries.setup_of()`, `walk()`, `stats()`/`scope()`, so a change to the walk's rules or to `setup_of()` changes the forward scores of the saved setups too (and `RULES[1:]` of its report), and `tests/test_score_entries.py` compares its results with `walk()`. It reads `entries[*]` through `setup_of()` plus `as_of`, `valid_until`, `asset.ticker` and `rules`; a schema change there needs it to follow, and a new rules version needs a line in its `RULES_MEANING`. It must keep reading files without `rules` (version 1) and keep the versions apart.
- **The setups' paths** are `trade_entries.paths()` (rules 3: `rz.walk()`'s first `PATHS` rows, bridged to days with `BRIDGE_SEED`, highs and lows with `SPREAD`). `garch_paths()` next to it (GARCH(1,1) volatility and Student-t days, `GARCH`, `GARCH_SPREAD`, `GARCH_SEED`) was evaluated as rules 4 and not adopted (README, "Rules version 4: clustering and fat tails, not adopted"); `setups()` must not call it, and it is kept only so that evaluation can be repeated (`examples/backtest_entries_2026-11-19_rules4*.txt` were made by swapping it in for `paths()` with the bands it measured). Any path model for the setups draws from its own generator and calls `rz.walk()` at most for its schedule or its unchanged draws: `tests/test_path_models.py` pins by hash the outputs that must never move with it (`rz.baseline()` at both sim methods, `mechanical.render(build())`, a `backtest.py` report). A new path model is a new `RULES` number with the whole procedure of README's rules sections: fit years only, `SPREAD` and `EDGE_BAND` measured again, judged once on the held-out year.
- **Tails** are zone entries with a `null` edge and ids `below`/`above`; the plot separates them from real zones by testing for `None`.
- **Sim method version**: `SIM_METHODS` in `rz.py` maps a version number to its rules (1: no drift, the original; 2: expected price +5% a year, `drift_of()`; none on intraday candles) and `SIM_METHOD` is the default of `sim`/`baseline()`. `baseline()` returns a `sim_method` block (`version`, `drift_per_year`, `drift_per_candle`), `rz.py sim --method N` and `backtest.py --method N` select an older one, `run_pipeline.rules_provenance()` records the checkout's default as `rules.sim_method` (read from the `SIM_METHOD = N` line as text, so keep that line's form), and SKILL.md tells Claude to name the version in `method`. A version's meaning never changes: a new rule gets a new number (and a row in the README table), and the old one stays runnable so saved baselines can be reproduced. `tests/test_rz.py` pins method 1's numbers to the original simulation. A change of default must be justified out of sample, the way the README's "Backtest of the baseline" section did for 2. There is no calibration table: the post-hoc calibration layer that was evaluated did not hold up across folds and was not shipped (README).
- **Scenario thresholds**: the plot recovers the middle-zone prices by regex from the scenario `low`/`high` strings (`"below 40.6"`), whose format comes from `rz.py sim`. Keep a number in those strings.
- **Swing markers** are drawn only if `structure.swing.*[1]` exactly equals a row's `start` string.
- **What a run prints** is read by `batch_runs.py`: the step headers that start Claude Code (`[2/N] Projection: Claude Code runs`, `[5/5] Trade setups: Claude Code writes`), the line `summary()` prints when a call ends (`done in`/`stopped after` ... `$X.XX`), the `Error: ` line, and the `input:` path on stdout. A call that started without its `summary()` line counts as an unknown cost, never zero. `tests/test_batch_runs.py::test_real_pipeline_runs_cost_folders_and_failures` runs the real pipeline in the child to pin these; change those strings only with it green.
- **Schema keys, ids and scenario names stay English** regardless of language; only free-text values are translated.
- **Schema versions and provenance.** The input carries `schema_version` (`build_prompt.SCHEMA_VERSION`) and `provenance`; the projection carries `schema_version` (SKILL.md's example; `rz.SCHEMA_VERSIONS` lists what `check` accepts); `provenance.json` has its own (`run_pipeline.PROVENANCE_VERSION`). All three are optional for readers: inputs and projections without them (every one made before, and `examples/` and `tests/fixtures/` on purpose) must still check, plot, score and show. Raise a version when a field changes meaning or goes away, and add the new value to `rz.SCHEMA_VERSIONS`. The model and cost never go into the projection: Claude cannot report them reliably, so `run_pipeline.py` reads them from the stream. `rz.saved()`, `list`, `score` and `show_run.py` must keep ignoring extra files in a saved folder (`entries.json`, `provenance.json`); `show_run.provenance_file()` and `run_pipeline.provenance_beside()` find the file next to a projection the same way. `tests/test_provenance.py` pins these.

### Things that are easy to get wrong

- One language setting: `build_prompt.py --language` (default `en`, free text) is stored as `reply.language`, sets the language of the projection's free text, and `plot_projection.py` follows it for the chart's own labels (`chart_language()`: primary subtag, so `pt-BR` -> `pt`; no `TEXT` entry or no `reply` -> `FALLBACK_LANG`). `--lang` has no default of its own: it is only an override, and it translates the labels, not the projection's text. A new chart language is one new `TEXT` entry, nothing else.
- Prices are split-adjusted but deliberately **not** dividend-adjusted (`auto_adjust=False`); the `drop` shock in `rz.py` and the chart footer depend on that.
- The project is installable only as an editable install, and is still not a package directory: the code is the root scripts. `pyproject.toml` has a `hatchling` build system and one entry point, `zones = "run_pipeline:main"`, whose wheel holds `run_pipeline.py` alone (`uv_build` cannot build a flat module). `run_pipeline.py` finds the other scripts and the skill next to its own file (`ROOT`) and runs Claude Code there, so `uv sync` and `uv tool install --editable .` work, and a non-editable install stops with a message saying so. Do not move the scripts without changing `ROOT`.
- The skill is a project skill, so Claude Code in this repo always uses the current files. A copy installed elsewhere (claude.ai, `~/.claude/skills/`) does not follow edits made here.
- `rz.py` must not be rewritten per run or have its seed changed: reproducible baselines are a design requirement.
- Session and week-end logic assumes a Monday-to-Friday exchange, so crypto tickers get wrong `forming` labels (listed under Known limits in the README).

## Domain constraint

One deliberate exception: ranked trade setups. `run_pipeline.py` ends with a step, on by default and skipped with `--no-entries`, that writes three hypothetical setups with entry, stop and target (`prompts/trade_entries.schema.json`). By default `trade_entries.py build` computes the whole file with no Claude call; with `--entries-by-claude` the step instead sends `prompts/trade_entries.md` (filled by `trade_entries.py prompt`) to a second `claude -p` call with no tools, run outside the repo, so that Claude writes the sentences. The rules are mechanical (prices from zone edges, odds counted on the input's simulated paths by `paths()`/`odds()`, ranked by the path edge per order, three always when three are valid, the best three whatever their side (rules 3; no side quota), with a plain limit line when none has a positive edge and another when all kept are on one side), and `trade_entries.py` implements the same rules in code: `build` writes and `check` recomputes every number, so **the template's rules and `setups()`/`pick()` must change together** (and a new free-text field needs wording in every `TEXT` language), and the JSON example at the end of the template must keep passing `check` against `examples/` (a test pins this). The precision rule (round prices to the candle rows' decimals, discard a zero risk, the "no setup passes" error) is stated in the template too. A failed check exits 1 but leaves the input, projection and chart in place. The step reads the projection's `supports`/`resistances` (`zone`, `id`), `structure.volatility.assumed`, `horizon.closes`/`last`/`close_basis`, `events` and `confidence`, and the input's candles, `now` and `want` through `rz.unpack()`/`rz.walk()` (so a change to `walk()`, `schedule()`, `vol()` or the default sim method changes the setups' odds), so a change to those fields in `SKILL.md` or to those rz.py functions needs a matching change here. The skill and the chart themselves still emit no stops or targets, and the setups carry no position size and never raise the confidence level.

The output is analysis, not advice: the skill and mechanical.py never emit buy/sell/hold calls, stops, targets or position sizes, and `confidence.level` is only ever `low` or `medium` (always `low` from mechanical.py). The probabilities of a projection are not backtested: `backtest.py` checks only the unadjusted baseline on mechanical zones, and its report keeps the caveats saying so. `backtest_entries.py` checks the stated odds of the mechanical engine's setups against later prices, and `score_entries.py` those of the setups real runs saved; it is a calibration check of hypothetical setups (no costs, pessimistic intra-candle ordering, survivor tickers), never a strategy or a returns claim, and its report keeps those caveats. `value_test.py` compares Claude's adjusted numbers with that baseline on dates after the model's training cutoff; its result (README, "Does Claude's adjustment help?") is a small sample. Preserve these constraints and the disclaimers when editing the skill, the chart footer or the README.
